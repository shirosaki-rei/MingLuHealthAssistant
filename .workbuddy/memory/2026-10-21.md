## 第三轮：架构设计文档

**产出**：docs/日常医疗健康平台_架构设计_v1.0.md（16 章 + 3 附录，约 700 行）

**PRD v3.1 架构视角评审：4 个 P0**
1. 支付无载体：`membership.channel` + `consult_order.price` 各自记账，缺 payment_intent / payment_transaction / refund_order → 回调重放会重复入账
2. 提醒频控矛盾：「主动关心每日 ≤1 次全端合计」(§6 L543) vs 「App 本地推送 + 本地数据触发」(L560)
3. 红旗 `logic_expr` 无语法定义（§12 L831 只说"明确表达式语法"）→ 规则引擎不可实现
4. 注销删除无传播范围：备份 7 天 + 对象存储 + 索引未纳入，与"已删除"承诺冲突

**P1**：对话流程红旗判断放在意图识别之后（含"胸痛"的句子会先进预问诊）；首字 2s 与全量后置校验冲突；知识库单条 800~1500 字塞不进 600t 预算。

**核心架构决策（12 条 ADR）**
- 模块化单体 + 独立 worker（3~4 人 / 11~13 周，禁微服务）
- PG16 单库：pgvector HNSW + **pg_bigm**（中文二元组，比 tsvector 更适合"氨氯地平"这类实体）+ RRF 融合 + rerank
- 调度用 PG `job` 表 `FOR UPDATE SKIP LOCKED`（不进 RabbitMQ），`dedupe_key` 保幂等
- 付费墙：action 白名单 `FREE_MEDICAL_ACTIONS` 前置到路由装饰器 + **CI AST 静态守卫**（就医路由文件里不许出现 membership/entitlement 符号）+ 12 条契约测试 → 误拦率 0 可证明
- 流式输出**按句缓冲**校验（用户永远看不到未校验文本，首字仍 <2s）
- 提醒频控**服务端唯一决策源**，客户端本地只能触发引导 UI 不计入推送
- 注销用**逐用户 DEK + crypto-shredding**（销毁密钥让备份内密文失效），不等备份过期
- 小程序 Taro 3 + `packages/domain` 三端复用；医生 H5 独立应用（微信服务号网页授权，需独立 appid，不能复用小程序 appid）

**开发顺序刻意安排**：safety 先于 chat（安全层是主链路门，后补等于重写编排）。

## 第八轮：首次真机联调结果

**H5 流式对话跑通** ✅（PoC 第 2 项的 H5 端完成，说明 SSE 解析 + 按句缓冲逻辑正确）

**终端两条 TS warning（非错误）**
1. `utils/stream.ts:85` fetch 行 "Object is possibly 'null'" —— uvue 的 lib 把 `AbortSignal`/fetch 返回声明得偏严格
2. `utils/stream.ts:93` `decoder.decode(value, { stream: true })` "Expected 1 arguments, but got 2" —— uvue 的 TextDecoder.decode 只声明 1 个参数

**修法**：`ctrl`/`reqInit`/`req`/`reader`/`decoder` 全部标 `any`（`const req: any = fetch(...)`），行为不变，仅过类型检查。

**安卓端两个失败（关键判断）**
- 流式失败显示 `[object Object]` → 走的是 `fail` 回调，**不是**"onChunkReceived 不存在"（那个会抛字符串）
- `uni.uploadFile` 报 `errCode 602001 / request system error`
- 两者都是**网络层失败**，请求根本没发出去/没回来

**推断根因**：Android 9+ 默认禁止明文 HTTP，`http://192.168.x.x:8787` 被系统拦截。这与"浏览器（H5）成功、App 全失败"的现象完全吻合。

**解法**：manifest.json 开 `usesCleartextTraffic=true`。uni-app x 的根节点是 `app`（不是 uni-app 的 `app-plus`）：
```json
"app": { "distribute": { "android": { "manifest": {
  "application": { "android:usesCleartextTraffic": "true" } } } } }
```
排查顺序：先手机浏览器开 `/health`（区分纯网络问题）→ 再看明文配置 → 最后才怀疑 API 差异。

**新增**
- `src/utils/err.ts`：`formatError()`，把 uvue 里 `[object Object]` 变成 errCode + errMsg 可读串
- `stream.uvue` 加「网络自检」按钮（直连 `/health`，fail 时提示"多为明文 HTTP 被拦或不在同一网段"）
- `camera.uvue` 四处错误全部改用 formatError

**待验证**：明文 HTTP 放行后，安卓端流式是否真的支持 `enableChunked`（这才是 PoC 第 2 项的真正结论）；以及 uploadFile 是否随网络恢复。

## 第十轮：PoC 关键结论 + 两个 bug 修复

**改 IP 后全部通过**
- 网络自检：通过
- **安卓端流式对话：通过（`uni.request` 的 `enableChunked` 在 uvue App 端可用）** ← PoC 最大风险项解除，后端不必改 WebSocket/轮询
- 按句缓冲：通过
- 图片压缩：778KB → 260.3KB（用服务端回显值，因为 uvue 没有可靠的本地取体积 API）

**Bug 1：传输完成后「清空」按钮失效**
根因：`reset()` 先调 `stop()` → `task.abort()`，请求已完成时 abort 抛异常，**后面的清空代码全被跳过**。中断时请求还在进行，abort 正常，所以只有"完成后"才暴露。
修法：`reset()` 里先清 UI 再 stop；`stop()` 的 abort 包 try/catch。

**Bug 2：上传按钮"没反应"**
两个原因：
1. 界面上那个 260.3KB 其实是压缩后**自动上传**拿到的服务端回显，第二次点上传返回同样的数，UI 无变化 = 看起来没反应
2. `uni.uploadFile` 的 `filePath` 对 `content://` 路径读不到

### 第十三轮补充 4：疑似仍在用标准基座

用户反馈 HBuilderX 提示「uts插件[minglu-alarm]依赖的原生配置或三方SDK在运行至标准基座时不能生效，如需正常调用请使用自定义基座」，且模拟触发仍无反应。

**新增诊断与兜底**
1. `isReceiverRegistered(context)`：用 `packageManager.queryBroadcastReceivers` 查 `MingluAlarmReceiver` 是否真的注册在 APK 里 —— 这是判断 manifest 合并成功与否最直接的证据，页面上显示「Receiver 注册：已注册/未注册」

4. 动态注册是 PoC 折中：**进程被杀后失效**，正式版仍必须解决静态注册

1. 先确认运行的是不是自定义基座（HBuilderX 那句提示就是判据）
2. 再看页面「Receiver 注册」是否为「已注册」

### 第十三轮补充 7：绕开自定义基座，改隐式广播

**日志铁证**：`"app":{"customBase":false}` + 进程名 `io.dcloud.uniappx` → 用户一直在跑**标准基座**，不是自定义基座。
标准基座里 UTS 的 Kotlin **确实能执行**（`dynamic receiver registered`、`fireNow sent` 都有日志），所以并不必须要自定义基座。

**真正的阻塞点**：`Intent(context, MingluAlarmReceiver::class.java)` 是**显式广播**，显式只投递给静态注册的组件，**匹配不到动态注册的 Receiver** → 标准基座里必然落空。

**改法（已执行）**
1. `fireNow` 与 `buildPendingIntent` 都改成隐式 Intent：`Intent(ML_ACTION_FIRE).setPackage(pkg)`，不指定 component
2. 根目录 AndroidManifest 给 `MingluAlarmReceiver` 加 `<intent-filter><action com.minglu.alarm.FIRE/></intent-filter>`（自定义基座场景用；`exported` 仍为 false，外部无法触发）

**自定义基座为什么点桌面图标会白屏**
调试基座启动时要连 HBuilderX 的 dev server 取资源，连不上就白屏等待，最后超时闪退。**手动点图标不是正确的启动方式**，必须从 HBuilderX 运行。

**结论**：优先让标准基座跑通（隐式广播 + 动态注册），自定义基座只作为"进程被杀后仍能唤醒"的最终方案。

**重启测试还差一次打包**：当前 APK 是 20:38 打的，AlarmReceiver 无 intent-filter 且 PendingIntent 还是隐式的，所以恢复的闹钟不会响。重打一次即可（manifest 已加 filter + PendingIntent 已改显式）。

## 第二十一轮：蒸汽模式三大约束（真机点出来才发现的，最贵的一轮）

**触发**：用户报「安卓不显示获取验证码按钮，浏览器和小程序正常」。

**已修复并真机验证**
1. 按钮不显示 = 原生 `input` 默认 `width:100%`（官方文档明示）+ 同行按钮被挤出容器。
   但真正根因是**后代选择器 `.codeRow .input` 在蒸汽模式被静默丢弃**（`css/common/selector.md`：蒸汽模式暂不支持关系选择器），
   所以之前 agent 加的 `width:0` 和我加的 `width:400rpx` 全都**没生效**。改成独立 class `codeInput` 后立刻好。
2. `display: block` / `inline-block` 是编译错误（只支持 flex|none），全项目 87 处已删。
3. `scroll-view` 的 `scroll-y` 已废弃 → `direction="vertical"`。

**三个运行时约束（各花好几轮编译，全是黑盒点出来的）**
1. **模板事件处理器里不能写赋值表达式**：`@tap="answer = o"`、`@click="showForm = false"` 被**静默忽略**。
   必须改成函数调用。全项目 5 处已改。
2. **动态 `:class` 不重算**：首次渲染对，状态变了样式不更新（对应文档「CSS 后设生效」）。
   **选中态一律用 `v-if` 渲染标记元素**（勾/徽标），不要动态 class。已全部改造。
3. **`ref` 对象不要改内部属性**：`form.value.xxx = y` 不触发更新，要 `form.value = {...form.value, xxx: y}`。
   （PoC 的 `utils/stream.ts` 早有同样注释，当时没看懂。）

**定位方法（关键教训）**
- `uiautomator dump` 拿不到 uvue 的文本节点，**截图 + PIL 量坐标**才靠谱；
  但 `adb shell input tap` 的坐标会被**软键盘弹起把页面顶滚动**搞失效，量完要确认页面没滚。
- **别用 `timeout` 掐掉 `cli.exe launch`**：标准基座靠调试连接转发事件，连接一断应用就"冻"住
  （不响应点击和返回键，画面停最后一张）——我因此误判了整整四轮"点击失灵"。
- `uni.showToast` 在调试基座里不可靠，别拿它当探针；用 `<text class="error">`（已知能渲染）。

**拉官方参考的收益**：clone 了 `hello-uni-app-x`（gitcode，放 /tmp/ref，没进项目）。
官方示例确认了 `<view @tap="fn(arg)">` + 条件 class 是标准写法，但它把 `@tap` 和动态 `:class`
放在**嵌套的两个 view 上**，且 class 名用 `computed` ref —— 这个差异指引了后面的方向。

**下一步建议**：把「模板禁赋值、选中态用 v-if、ref 整体替换」三条写进项目规范，
否则新页面一定还会再犯。已写进 `android/README.md`。

**发现并修复的真实缺陷：红旗漏检**

输入「我胸口疼得厉害，喘不上气，冷汗直流」→ **红旗没触发**。
原因：规则里写的是「胸**痛**」「喘**不**过气」，用户说的是「胸**口**疼」「喘**不**上气」，差一个字就漏。

已补关键词：
- chest_pain: 加 胸口疼/胸口痛/前胸疼/前胸痛/心口痛/心前区痛/胸部压着，any_of 加「冷汗」
- dyspnea: 加 喘不上气/上不来气/透不过气/呼吸急促

复测：胸痛→chest_pain 触发 ✓、卒中→stroke 触发 ✓、普通头晕不误报 ✓。pytest 31 个仍全过。

**教训**：红旗关键词必须按**口语**覆盖，不能只写书面语。这条规则的价值不在于技术，在于覆盖度，而覆盖度只能靠真实语料反复喂。

**另一个发现（产品逻辑正确）**：提醒接口会拒绝 23:00-7:00 的触发时间（静默时段），演示脚本的 +8 小时正好撞上 → 已加 `safe_time()` 自动顺延到次日 8 点。
