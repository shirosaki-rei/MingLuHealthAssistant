# 明路 · 架构设计（V1.0）

> 依据：《明路 PRD v3.1》《明路 PoC 验证方案 v1.0》及其实测结论
> 技术栈：uni-app x（三端同源）+ FastAPI + PostgreSQL 16
> 编写日期：2026-10-21
> 状态：可作为开发启动依据；标注「待定」的部分不阻塞开工

---

## 0. 前置结论（来自 PoC 实测，不是推演）

架构的前提是技术选型成立。以下每条都有实测证据，不是假设：

| 结论 | 证据 | 对架构的影响 |
|---|---|---|
| 一套代码可出安卓 / 小程序 / H5 | 同一份 `.uvue` 三端构建通过 | 客户端只维护一套代码，`packages/domain` 不必强拆 |
| 安卓端 SSE 流式可用 | `uni.request` + `enableChunked` 实测通过 | **后端用 SSE，不需要 WebSocket** |
| 小程序端流式可用 | 同上，需关 `urlCheck` | 后端接口一套 |
| 小程序分包与预加载可用 | `subPackages` + `preloadRule` 生效 | 报告预览、趋势图可放心塞分包 |
| 精确闹钟息屏可触发 | 60 秒测试，息屏后准时收到 | 用药提醒成立；需 ROM 白名单 |
| 开机恢复需静态注册 | 标准基座无 manifest，动态注册收不到 `BOOT_COMPLETED` | 提醒调度必须按「静态注册 + 自定义基座」设计 |
| 未验证：8 小时长时延 | 待观察 | 首版把提醒精度承诺写保守（±1 分钟），不做「准点」宣传 |

**一条硬约束**：包含原生代码的 UTS 插件必须用自定义基座，标准基座跑不了开机恢复。这不是可以绕过的，写进开发环境的强制要求。

## 1. 架构驱动因素

技术决策从约束反推，不从喜好出发。

| # | 驱动因素 | 约束 | 对应决策 |
|---|---|---|---|
| 1 | 团队 3~4 人、12~14 周 | 人力极少 | 模块化单体，不拆微服务 |
| 2 | 三端同源 | 需要一份代码 | uni-app x + 统一 API |
| 3 | 医疗安全不可降级 | 安全层必须独立于模型 | 规则引擎独立进程内模块，纯代码 |
| 4 | 健康数据敏感 | 境内存储、不出境 | 模型/OCR/ASR 全部境内，网关层做出口白名单 |
| 5 | 付费墙不能误拦就医 | 需要可验证 | 服务端唯一判定 + 路由级白名单 + 契约测试 |
| 6 | 成本敏感 | 单用户推理成本 2~4 元 | 上下文压缩 + 缓存 + 配额 |
| 7 | 提醒要准时 | 需要原生能力 | UTS 插件 + 静态 Receiver + 精确闹钟 |

## 2. 模块划分与依赖规则

### 2.1 后端目录

```
services/api/
├── modules/
│   ├── identity/       登录、会话、设备
│   ├── profile/        就诊人档案（多档案）
│   ├── persona/        角色配置与审核
│   ├── chat/           对话编排（L0 四道防线在这里串起来）
│   ├── preconsult/     预问诊状态机
│   ├── knowledge/      知识库、检索、引用快照
│   ├── safety/         红旗规则、注入检测、输出校验
│   ├── match/          科室映射、医生排序
│   ├── consult/        订单状态机、支付、争议
│   ├── health/         打卡、报告、时间线、摘要导出
│   ├── reminder/       提醒 CRUD 与调度
│   ├── entitlement/    会员与权益判定
│   └── admin/          运营后台接口
├── platform/
│   ├── llm_gateway/    模型调用、重试、降级、成本计量
│   ├── db/             连接池、迁移
│   ├── job/            PG 任务队列
│   ├── storage/        对象存储（报告图片）
│   └── obs/            日志、指标、追踪
└── app.py
```

### 2.2 依赖规则（写进 CI）

| 规则 | 原因 |
|---|---|
| `modules` 之间只能通过 `service` 层调用，禁止跨模块直接查表 | 防止 12 个模块长成一坨 |
| `safety` 不得依赖 `llm_gateway` | 红旗必须能在模型全挂时生效 |
| `entitlement` 被所有人调用，但它不得反向依赖任何业务模块 | 避免循环依赖 |
| `platform` 不知道 `modules` 的存在 | 基础设施保持无业务 |
| 所有对外接口必须经过 `safety.precheck` 与 `safety.postcheck` | 四道防线不能漏 |

用 `import-linter` 做静态检查，违反直接 CI 失败。

### 2.3 为什么是单体

3~4 人的团队维护 12 个模块的服务，拆成微服务意味着 12 套部署、12 份日志、12 处网络故障点。模块化单体用目录边界 + import 规则就能获得 90% 的好处，剩下 10% 留到真的需要时再拆。

拆分信号（明确写下来，避免以后拍脑袋）：单一模块的 CPU 或内存占比超过 40%，或某个模块需要独立发布频率。

## 3. 数据模型

### 3.1 核心关系

```
user 1─n patient_profile 1─n health_record
                          ├─n report_doc
                          ├─n timeline_event
                          └─n pre_consult

user 1─n persona（预设 / 自定义）
user 1─n conversation 1─n message 1─n kb_citation
user 1─1 membership
user 1─n consult_order 1─n consult_message
user 1─n reminder
user 1─n consent_log

department 1─n doctor 1─n consult_order
kb_entry n─1 department
```

### 3.2 关键表设计要点

| 表 | 设计要点 |
|---|---|
| `patient_profile` | 归属 `user_id`，一人最多 6 个；`relation` 区分本人/家人；代述时 `is_proxy` 打标 |
| `persona` | 存结构化字段（name / species / self_ref / catchphrase / worldview / tone[]），**不存自由 prompt** |
| `message` | `source_refs[]` 存引用，同时写 `kb_citation` 快照（含 entry_version），词条更新后可回溯 |
| `agent_memory` | KV 结构，`type` 分 fact/pref/event；`confirmed_at` 记录用户确认时间 |
| `reminder` | `cron` + `next_fire_at` + `channel`；客户端只缓存，**服务端是唯一决策源** |
| `consult_order` | 金额拆 `price / platform_fee / doctor_income / tax_amount`，结算可对账 |
| `kb_entry` | `version` + `valid_until` + `reviewer_license`；过期自动下线 |
| `ai_log` | 明文 30 天 → 哈希 6 个月；`input/output` 落库前掩码手机号、身份证、姓名 |
| `consent_log` | 授权类型、版本、时间、IP、场景；PIPL 举证用 |
| `notify_log` | 每次推送一条，用于频控与合规举证 |

### 3.3 索引策略

| 场景 | 索引 |
|---|---|
| 按就诊人查健康记录 | `(patient_id, measured_at desc)` |
| 时间线倒序 | `(patient_id, occurred_at desc)` |
| 对话历史 | `(conversation_id, created_at)` |
| 提醒调度扫描 | `(next_fire_at) where status = 'pending'` |
| 医生列表按科室 | `(department_code, online_status)` |
| 知识库检索 | `pgvector` HNSW + `pg_bigm` GIN（中文二元组，适合"氨氯地平"这类实体） |

### 3.4 检索方案

医疗术语的精确匹配很关键，纯向量会丢实体。采用**混合检索**：

```
query → 向量检索 Top20（pgvector, HNSW）
      → 全文检索 Top20（pg_bigm）
      → RRF 融合 → Rerank 取 Top3
```

上线门槛：100 条标注问答集，Top1 ≥80%，Top3 ≥92%。

## 4. 接口契约

### 4.1 约定

- 全量 REST + 一个 SSE 端点
- 鉴权：`Authorization: Bearer <token>`
- 所有响应带 `request_id`，与 `ai_log` 对齐
- 错误码：`{ code, message, request_id }`，`code` 用业务语义而非 HTTP 状态

### 4.2 核心端点

| 方法 | 路径 | 要点 |
|---|---|---|
| POST | `/v1/auth/sms` | 发送验证码，限流 1 次/60s |
| POST | `/v1/auth/login` | 手机号 + 验证码，返回 token |
| GET | `/v1/patients` | 多档案列表 |
| POST | `/v1/patients` | 建档案，未成年人需 `guardian_consent` |
| GET | `/v1/personas` | 预设 + 我的角色 |
| POST | `/v1/personas` | 创建角色，走审核队列 |
| POST | `/v1/chat/stream` | **SSE**，逐句推送，首字 <2s |
| GET | `/v1/chat/history` | 分页，支持 hidden 过滤 |
| POST | `/v1/preconsult/start` | 返回首问，建状态机 |
| POST | `/v1/preconsult/answer` | 提交一轮答案，返回下一问或病历 |
| POST | `/v1/preconsult/finish` | 生成结构化病历 |
| POST | `/v1/match/departments` | 症状 → Top3 科室 + 置信度 |
| GET | `/v1/doctors` | 按科室 + 排序权重 |
| POST | `/v1/orders` | 下单，生成支付单 |
| GET | `/v1/orders/{id}` | 状态机查询 |
| POST | `/v1/reminders` | 建提醒，返回服务端计算的下次触发时间 |
| GET | `/v1/reminders/pending` | 客户端拉取需本地注册的闹钟 |
| POST | `/v1/reports` | 上传报告，异步 OCR |
| GET | `/v1/reports/{id}` | 指标 + 解读 |
| GET | `/v1/timeline` | 时间线分页 |
| POST | `/v1/timeline/export` | 生成就诊摘要，返回带 token 的链接 |
| GET | `/v1/membership` | 当前权益 |
| GET | `/v1/config/medical-actions` | **就医路径白名单**，客户端缓存 |
| GET | `/v1/redflag/rules` | 红旗规则版本（客户端离线兜底用） |

### 4.3 SSE 协议

```
event: delta
data: {"delta":"先别急着下结论。"}

event: done
data: {"usage":{"in":2100,"out":320},"request_id":"..."}
```

- 服务端**按句缓冲**推送，不推半句（这是后置校验能生效的前提）
- 客户端收到 `delta` 后逐句渲染，不拼半句
- 断线重连：客户端带 `last_event_id`，服务端从断点续推（首版可简化为重发全量）

### 4.4 就医路径白名单的落地

这是红线，必须有可验证的机制，不能靠自觉：

```python
# modules/entitlement/policy.py
MEDICAL_ACTIONS = frozenset({
    "preconsult.start", "preconsult.answer", "preconsult.finish",
    "match.departments", "doctor.list", "doctor.detail",
    "order.create", "order.pay",
    "safety.redflag", "safety.crisis",
    "patient.list", "patient.create",
    "timeline.read", "memory.read", "memory.delete",
})

def require_entitlement(action: str, user):
    if action in MEDICAL_ACTIONS:
        return  # 永远放行，不读 membership
    ...
```

配套三道保障：

1. **路由装饰器**：所有接口显式声明 action，未声明直接 500（防止漏配）
2. **静态检查**：`modules/entitlement` 之外的文件不得出现 `membership` 符号
3. **契约测试**：12 条用例覆盖「未开通 / 已过期 / 已灰产」，全部断言 200

## 5. 关键链路

### 5.1 对话（L0 四道防线的位置）

```
客户端 POST /chat/stream
  → ① 输入检测（注入关键词 + 正则，<50ms）
  → ② 红旗检测（纯规则，<20ms）—— 命中则短路，直接返回急救指令
  → ③ 意图识别（小模型或规则，<300ms）
       ├ 求诊断 → 转预问诊
       └ 健康问答 → 检索（<250ms）→ 生成（流式）
  → ④ 逐句后置校验 → 通过才推给客户端
  → ⑤ 落 ai_log（掩码后）
```

**关键设计**：红旗检测放在意图识别**之前**。否则「我胸痛，挂什么科」会先进科室匹配，延迟急救引导。这是 PRD 评审里发现的问题，架构上直接修掉。

**后置校验与流式的矛盾**：不能等全文生成完再校验，那样首字延迟就废了。做法是**按句缓冲**——每凑够一个完整句子就校验，通过了才推。用户永远看不到未校验的文本，首字延迟仍 <2s。

### 5.2 预问诊

```
start → 建 pre_consult(status=asking, round=0)
  → 每轮 answer：写入 structured_json，round++
  → round ≥ 6 或用户喊停 → 强制 finish（标注「信息较少」）
  → 任意一轮命中红旗 → 中断，status=aborted_redflag
  → finish：生成病历草稿，status=confirming
  → 用户确认 → status=done，写 timeline_event
```

中断可续接：`status=asking` 的记录保留，再次进入读 `round` 与已答字段。

### 5.3 提醒调度（客户端 + 服务端）

```
服务端：reminder 表 + next_fire_at，定时任务每分钟扫描
  → 到点前 24h 把「未来 24h 的提醒」推给客户端（/reminders/pending）
客户端：收到后本地注册精确闹钟（UTS 插件）
  → App 启动时重新拉取，做一次全量重排（兜底）
  → 开机后由 BootReceiver 从 SharedPreferences 恢复
```

**为什么不服务端直接推**：推送到达率与准时性都不可控，而用药提醒要求分钟级精度。服务端只负责"算出该什么时候响"，客户端负责"真的响"。

**已知限制**：开机恢复依赖静态注册，必须自定义基座；标准基座下只能在 App 启动时重排。这条写进技术债。

## 6. 客户端架构

### 6.1 分层

```
pages/（.uvue 页面）
  ↓
composables/（页面逻辑，组合式函数）
  ↓
stores/（Pinia，跨页状态）
  ↓
api/（请求封装，统一处理 token 与错误）
  ↓
utils/（纯函数：SSE 解析、按句缓冲、错误格式化）
```

规则：页面不直接调 `uni.request`；`utils` 不依赖 `stores`。

### 6.2 条件编译边界

只用三种平台标识，且必须精确：

| 标识 | 含义 | 常见误用 |
|---|---|---|
| `#ifdef H5` | 浏览器 | — |
| `#ifdef MP-WEIXIN` | 微信小程序 | — |
| `#ifdef APP` | 安卓 App | **不要用 `#ifndef H5` 代替 `#ifdef APP`**，它会把小程序也圈进去（本项目已踩过） |

### 6.3 原生模块

只有一个：`minglu-alarm`（精确闹钟 + 开机恢复）。其余全部用 uni 标准能力，不引入三方原生 SDK。

## 7. 部署与运维

### 7.1 拓扑

```
Nginx（TLS、静态资源、SSE 直通）
  ├── /api  → FastAPI（2 实例，uvicorn）
  ├── /h5   → 静态文件
  └── /admin → 静态文件

PostgreSQL 16（主库）
Redis（会话、频控、SSE 连接计数）
对象存储（报告图片，私有桶 + 签名 URL）
```

单机 Docker Compose 起步（4C8G），日活过万再考虑拆分。

### 7.2 关键运维项

| 项 | 策略 |
|---|---|
| 备份 | PG 每日全量 + WAL 增量，保留 7 天；每周做一次恢复演练 |
| 日志 | request_id 贯通；应用日志 7 天，`ai_log` 按合规要求 |
| 监控 | 首字延迟、SSE 断流率、模型错误率、红旗命中数、付费墙放行数 |
| 告警 | 首字 P95 >3s、SSE 失败率 >2%、模型连续失败 5 次 |
| 降级 | 模型全挂 → 关闭问答，保留检索与预问诊模板；DB 挂 → 静态降级页 |

### 7.3 发布

- 后端：蓝绿部署，迁移用 Alembic，禁止在发布脚本里跑 DDL
- 客户端：小程序审核 + 安卓五商店，预留 2~3 周
- 灰度：先用 10% 用户跑新规则/新模型，异常一键回滚

## 8. 非功能落地

### 8.1 时延预算（首字 2s 的分解）

| 环节 | 预算 |
|---|---|
| 输入检测 | 50ms |
| 红旗检测 | 20ms |
| 意图识别 | 300ms |
| 检索 + Rerank | 250ms |
| 模型首 token | 1000ms |
| 首句校验 | 100ms |
| 网络与渲染 | 280ms |
| **合计** | **2000ms** |

任何一环超预算，必须在监控上能看到。

### 8.2 成本控制

| 手段 | 效果 |
|---|---|
| 记忆结构化（不堆原始对话） | 上下文从 8K 降到 3.3K |
| 知识检索结果截断到 600t | 单轮省 30% |
| 相同问题缓存（1h） | 常见问题命中率约 15% |
| 日 200 轮上限 | 防单用户打爆 |

### 8.3 安全与合规的架构级要求

| 要求 | 落点 |
|---|---|
| 模型不出境 | `llm_gateway` 只允许配置境内 base_url，白名单硬编码 |
| 红旗不依赖模型 | `safety` 纯规则，模型挂了照常工作 |
| 日志可举证 | `ai_log` + `consent_log` + `notify_log` 三表 |
| 删除可执行 | 逐用户 DEK 加密，删号即销毁密钥（crypto-shredding），不必等备份过期 |

## 9. 技术债与已知限制

| # | 限制 | 影响 | 何时处理 |
|---|---|---|---|
| 1 | 开机恢复依赖自定义基座 | 开发与测试必须用 `--playground custom`；正式包不受影响 | 已在 PoC 中跑通，非阻塞 |
| 2 | 动态注册的 Receiver 在进程被杀后失效 | 标准基座下的兜底能力有限 | 正式包用静态注册，已解决 |
| 3 | 小程序首屏受 VDOM 限制 | 冷启动可能超 1.5s | 分包 + 骨架屏，二期优化 |
| 4 | 蒸汽模式 2026 年新出 | 潜在未知 bug | 保留关蒸汽模式回 VDOM 的退路 |
| 5 | **8 小时长时延未实测** | 极端 Doze 下的精度未知 | 开发期用测试机常驻补测；在此之前文案不承诺"准点"，只写"按时提醒" |
| 6 | 医生端仅 H5 | 移动端体验一般 | 视医生反馈，二期再评估 |
