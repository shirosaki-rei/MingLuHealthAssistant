# 红线与架构约束

> **什么时候读这个文件**：改付费墙/会员逻辑、加新模块或新接口、改对话链路或提醒调度。
> **什么时候可以删**：永不。但「拆分信号」那类带条件的条目，条件达成时可以删。

## 一、付费墙是产品红线

`/v1/config/medical-actions` 返回的 action，服务端**永远放行，不读会员状态、不做限额降级**：

- **就医路径**：预问诊、科室推荐、医生、下单支付、红旗急救、多就诊人档案、时间线、记忆管理
- **自有数据读写**：列表/详情/删除一律放行（会员过期只收回增强能力，不收回数据）

可以收费的**只有消耗型动作**：对话轮次、报告解读次数、提醒条数、自定义角色。
对话触顶只给三条出口（找医生/看知识/明天再来），**不弹阻断式付费墙**。

### 三道保障，缺一不可

1. **路由装饰器**：所有 `/v1/*` 路由必须显式声明 action，未声明或拼错 → 启动时
   `RuntimeError`，进程起不来（`app/main.py` 的 `_assert_all_actions_declared`）
2. **静态检查**：`modules/entitlement` 之外不得出现 `membership` 符号
3. **契约测试**：`tests/test_contract.py` 覆盖未开通/已过期/已灰产，全部断言 200

- **来源**：PRD §1.4 红线 + 架构 §4.4。付费墙误拦就医人身系产品定性，
  光靠 code review 守不住。
- **适用**：任何新增接口、任何改 `entitlement.py` 的动作。
- **过期**：永不。

### 新增 action 的流程

往 yaml 的 `/v1/config/medical-actions` 清单里加 → 同步 `services/api/app/modules/entitlement.py`
的 `MEDICAL_ACTIONS` → 两边不一致由 `test_architecture.py::test_contract_action_list_matches_code`
兜住（会红）。

## 二、模块化单体，依赖规则写进 CI

`services/api/app/modules/` 13 个模块。规则：

| 规则 | 原因 |
|---|---|
| 模块之间**只能通过 service 层调用**，禁止跨模块直接查表 | 防止 12 个模块长成一坨 |
| `safety` 不得依赖 `llm_gateway` | 红旗规则必须能在模型全挂时生效 |
| `entitlement` 被所有人调用，但**不得反向依赖任何业务模块** | 避免循环依赖 |
| `platform` 不知道 `modules` 的存在 | 基础设施保持无业务 |
| 所有对外接口必须经过 `safety.precheck` 与 `safety.postcheck` | 四道防线不能漏 |

由 `tests/test_architecture.py` 静态断言，违反直接测试红。

**为什么是单体**：3~4 人团队维护 12+ 个模块的服务，拆微服务意味着 12 套部署、12 份日志、
12 处网络故障点。模块化单体用目录边界 + import 规则就能拿到 90% 的好处。

**拆分信号**（明确写下来，避免以后拍脑袋）：单一模块的 CPU 或内存占比超过 40%，
或某个模块需要独立发布频率。—— *条件达成时这一条就可以删了。*

## 三、医疗安全的四道防线

在 `modules/chat.py` 串起来，顺序是故意的：

```
输入检测（注入关键词+正则，<50ms）
  → 红旗检测（纯规则，<20ms）        ← 在意图识别之前！
  → 意图识别（<300ms）
       ├ 求诊断 → 转预问诊
       └ 健康问答 → 检索（<250ms）→ 生成（流式）
  → 逐句后置校验 → 通过才推给客户端
  → 落 ai_log（掩码后）
```

**红旗必须放在意图识别之前**：否则「我胸痛，挂什么科」会先进科室匹配，延迟急救引导。
这是 PRD 评审里发现的问题，架构上直接修掉了。

**后置校验与流式的矛盾**：不能等全文生成完再校验（首字延迟就废了），也不能推半句
（用户会看到未校验文本）。做法是**按句缓冲**——每凑够一个完整句子就校验，通过了才推。

- **来源**：PRD §14 + 架构 §5.1。
- **适用**：改对话编排、改 SSE、改红旗规则。
- **过期**：永不。

## 四、提醒调度：服务端算时间，客户端负责响

```
服务端：reminder 表 + next_fire_at，定时任务每分钟扫描
  → 到点前 24h 把「未来 24h 的提醒」推给客户端（/reminders/pending）
客户端：收到后本地注册精确闹钟（UTS 插件）
  → App 启动时重新拉取，做一次全量重排（兜底）
  → 开机后由 BootReceiver 从 SharedPreferences 恢复
```

**为什么不服务端直接推**：推送到达率与准时性都不可控，而用药提醒要求分钟级精度。
服务端只负责「算出该什么时候响」，客户端负责「真的响」。客户端不做重复规则计算。

**开机恢复必须静态注册 Receiver + 自定义基座**，标准基座收不到 `BOOT_COMPLETED`。
PoC 已跑通（60 秒息屏准时触发 + 重启恢复）。

⚠️ **当前状态**：`minglu-alarm` UTS 插件只在 `uni-appX/uni_modules/`，
`android/` 还没接。所以 `android/pages/reminder/reminder.uvue` 只做 CRUD 与展示，
不注册本机闹钟。**接了插件后才需要 `--playground custom`**。

- **来源**：架构 §5.3 + PoC 实测结论。
- **适用**：改提醒链路、接闹钟插件。
- **过期**：`android/` 接上闹钟插件后，「当前状态」那段可删。

## 五、其他合规相关的架构级要求

| 要求 | 落点 |
|---|---|
| 模型不出境 | `llm_gateway` 只允许配置境内 base_url，白名单在 `platform/llm.py` 硬编码；加新厂商必须走评审，不允许运行时注入任意 URL |
| 红旗不依赖模型 | `safety` 纯规则，模型挂了照常工作 |
| 日志可举证 | `ai_log` + `consent_log` + `notify_log` 三表；`ai_log` 明文 30 天 → 哈希 6 个月，落库前掩码手机号/身份证/姓名 |
| 删除可执行 | 逐用户 DEK 加密，删号即销毁密钥（crypto-shredding），不必等备份过期 |
| request_id 贯通 | 中间件注入，与 `ai_log` 对齐；出错时同时在错误体里 |

- **来源**：架构 §8.3。
- **适用**：改平台层、改日志、改删除逻辑。
- **过期**：永不。
