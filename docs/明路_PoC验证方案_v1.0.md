# 明路 PoC 验证方案（V1.0）

> 目的：验证「uni-app x 蒸汽模式一套代码出安卓 + 小程序 + H5」在本项目的关键链路上成立  
> 周期：10 个工作日  
> 产出：通过 / 降级 / 失败 的明确结论 + 可复用的适配层代码  
> 编写日期：2026-10-21

---

## 0. 目的与边界

PoC 不验证业务，只验证**技术假设**。不做的事：不做登录、不做真实 AI 接口、不做 UI 还原、不接支付。

只回答一个问题：**这套技术栈能不能撑住明路的四个关键动作**。

| 关键动作  | 为什么是它                         |
| ----- | ----------------------------- |
| 流式对话  | 产品 80% 的时间花在对话上，流式断了体验就废      |
| 拍照上传  | 报告识别是核心卖点，相机 + 压缩 + OCR 链路不能卡 |
| 精确闹钟  | 用药提醒的命门，也是最可能逼你写原生插件的地方       |
| 小程序分包 | 主包 2MB 是硬限制，超了直接传不上去          |

---

## 1. 五项验证与通过标准

| # | 验证项        | 通过标准                                  | 权重 |
| - | ---------- | ------------------------------------- | -- |
| 1 | **三端同源构建** | 同一份代码产出 APK、微信小程序、H5，无分叉分支            | 必须 |
| 2 | **流式对话**   | 三端均能逐字/逐句渲染；首字 <2s；能按句缓冲做后置校验         | 必须 |
| 3 | **拍照上传**   | 相机调起 → 压缩至 ≤500KB → 上传 → 回显，安卓与小程序均可用 | 必须 |
| 4 | **精确闹钟**   | 锁屏 8 小时误差 <1 分钟；重启后能恢复；国产 ROM 至少一台可用  | 必须 |
| 5 | **小程序分包**  | 主包 ≤2MB，分包预加载生效                       | 重要 |

**判定规则**：1~4 全过 = 通过；第 2 或第 4 项不过 = 触发降级；第 1 项不过 = 方案失败。

---

## 2. 环境准备

| 项         | 要求                                              | 备注                   |
| --------- | ----------------------------------------------- | -------------------- |
| Node      | 22 LTS                                          | 与托管环境一致              |
| 包管理       | pnpm 9+                                         | monorepo 用           |
| HBuilderX | **5.21+**                                       | 蒸汽模式安卓需要；低于此版本不出蒸汽模式 |
| 微信开发者工具   | 最新稳定版                                           | 基础库 2.25+            |
| 安卓真机      | **至少 1 台 Android 12+**，最好再有一台国产 ROM（小米/华为/OPPO） | 精确闹钟必须在真机测，模拟器无效     |
| 后端桩       | 一个本地 Node 服务，返回 SSE 流                           | 不接真实模型，省成本           |

> **已知工程限制**：H5 与小程序可以纯 CLI 构建，**安卓端必须依赖 HBuilderX（或云打包）**。这意味着 CI 无法覆盖安卓出包，需要在流程里留一个人工步骤。这一点写进架构约束。

## 3. 工程创建

```bash
# 方式一：官方模板（推荐先试这个）
npx degit dcloudio/uni-preset-vue-x minglu-poc
cd minglu-poc && pnpm install

# 方式二：官方脚手架
npm create uni-app-x@latest minglu-poc
```

创建后确认三件事：

1. `manifest.json` 里**蒸汽模式已开启**（可视化界面首页勾选）
2. `package.json` 里有 `dev:h5` / `dev:mp-weixin` / `dev:app`
3. 用 HBuilderX 打开工程，能识别为 uni-app x 项目（不是普通 uni-app）

```bash
pnpm dev:h5          # 浏览器
pnpm dev:mp-weixin   # 产物在 dist/dev/mp-weixin，用微信开发者工具打开
# 安卓：HBuilderX → 运行 → 运行到手机或模拟器
```

## 4. 验证项详情

### 4.1 三端同源构建

**做法**：写一个页面，含文本、图片、列表、输入框、按钮，三端各跑一遍。

**通过标准**：

- 同一份 `.vue` 文件，三端都能编译，无 `#ifdef` 分叉
- 布局在三端视觉一致（允许 1~2px 差异）
- 无"某端组件不存在"的报错

**失败对策**：记录具体是哪个组件/样式不支持。若只是个别组件，可接受（用条件编译局部处理）；若是布局体系不兼容（如 flex 行为差异大），触发降级。

---

### 4.2 流式对话（最高风险项）

**风险点**：三端的流式 API 不统一，这是"一套代码"最容易裂开的地方。

| 端             | 可行方案                                                     | 风险           |
| ------------- | -------------------------------------------------------- | ------------ |
| H5            | `fetch` + `ReadableStream`                               | 低            |
| 微信小程序         | `wx.request` 的 `enableChunked: true` + `onChunkReceived` | 中，需基础库 2.20+ |
| 安卓（uni-app x） | `uni.request` 是否支持 chunked **待验证**                       | **高**        |

**做法**：

1. 起一个本地 SSE 桩服务，每秒推一个汉字，共 50 字
2. 三端各写一个最小页面接收并渲染
3. 记录：首字时间、渲染是否连续、能否中途取消

**通过标准**：

- 三端首字 <2s
- 逐字渲染不卡顿，无整段一次性蹦出
- 能按句缓冲：收到句号/问号才渲染，未完成的句子不显示

**若安卓端不支持 chunked 的退路**（按顺序试）：

1. 改用 WebSocket（三端都支持，但要改后端为 WS 协议）
2. 改用 HTTP 轮询（每 500ms 拉增量，体验差一档，但稳）
3. 安卓端单独写 UTS 插件走原生 OkHttp 流式

> 这一项的结论会直接改变后端接口设计，所以必须最先验。

---

### 4.3 拍照上传 + OCR

**做法**：

1. `uni.chooseImage`（或 uni-app x 对应 API）调起相机
2. 压缩到 ≤500KB（长边 1600px，JPEG 质量 0.7）
3. 上传到本地桩服务，回显图片
4. 桩服务返回一段假 OCR 结果，页面渲染成指标列表

**通过标准**：

- 安卓与小程序都能调起相机
- 压缩后体积达标，肉眼无明显糊
- 上传成功率 100%（局域网）
- H5 端可选（仅验证 `input capture` 是否可用，不作为必须）

**记录**：安卓端首次申请相机权限的弹窗时机是否符合"首次使用场景申请"的要求（这是上架审核项）。

---

### 4.4 精确闹钟（工作量最大）

**为什么难**：用药提醒必须准时，而安卓的后台限制逐年收紧。

| 障碍                     | 说明                                |
| ---------------------- | --------------------------------- |
| `SCHEDULE_EXACT_ALARM` | Android 12+ 需声明；13+ 部分场景需引导用户手动授权 |
| 后台限制                   | Doze 模式会推迟非精确闹钟                   |
| 开机恢复                   | 重启后闹钟丢失，需监听 `BOOT_COMPLETED` 重新注册 |
| 国产 ROM                 | 小米/华为/OPPO 会杀后台，需引导加自启动白名单        |

**做法**：

1. 用 UTS 写一个最小插件，封装 `AlarmManager.setExactAndAllowWhileIdle`
2. 注册 `BOOT_COMPLETED` 广播接收器，开机后重排所有未触发的闹钟
3. 触发时发本地通知（`NotificationManager`）
4. 页面提供"设定 1 分钟后提醒"按钮，方便反复测

**通过标准**：

- 设定 3 个闹钟（1 分钟 / 30 分钟 / 8 小时），锁屏待机
- 前两个误差 <10 秒，8 小时那个误差 <1 分钟
- 重启手机后，未触发的闹钟仍能响
- 在至少一台国产 ROM 上验证；若失败，记录需要用户手动开哪些开关

**失败对策**：

1. 若只是国产 ROM 杀后台 → 不算技术失败，转为产品方案：首次设置提醒时引导用户加白名单（要有图文引导页）
2. 若 `setExactAndAllowWhileIdle` 在本机型被系统限制 → 降级为"精确到 ±15 分钟"的 `setWindow`，并在 UI 上说明
3. 若 UTS 插件写不出来 → 这是硬伤，因为提醒是留存支柱，需要考虑安卓端改原生

> 这一项如果失败，"一套代码"的收益要重新算：安卓要单独写，人力 +1。

---

### 4.5 小程序分包

**做法**：

1. 故意把报告预览、趋势图、角色编辑三个页面放进分包
2. 配置 `preloadRule`，首页预加载报告分包
3. 用微信开发者工具看主包体积

**通过标准**：

- 主包 ≤2MB
- 分包能正常跳转
- 预加载生效（看 Network 面板）
- 分包间公共代码抽到主包，无重复打包

**注意**：第三方 UI 库如果全量引入，很容易超 2MB。这一项同时也验证"不用第三方组件库"的决定是否必要。

## 5. 判定矩阵

| 结果       | 条件                       | 后续                                            |
| -------- | ------------------------ | --------------------------------------------- |
| **通过**   | 1~4 全过                   | 按 uni-app x 三端同源推进架构设计，进入开发                   |
| **降级 A** | 流式在安卓端不可行，但 WebSocket 可行 | 后端改用 WS 或轮询；架构文档记一条 ADR                       |
| **降级 B** | 精确闹钟在国产 ROM 不可靠          | 保持同源，但产品侧加"白名单引导"流程，提醒精度承诺下调                  |
| **降级 C** | 蒸汽模式整体不稳（UI 渲染异常、崩溃）     | 关蒸汽模式回 VDOM，代码不改，接受性能降级                       |
| **失败**   | 三端同源无法成立                 | 安卓改 Kotlin 原生，小程序/H5 保留 uni-app；人力 +1，周期 +3 周 |

## 7. PoC 结束要产出什么

1. **结论报告**：五项逐条给通过/降级/失败，附证据（截图、耗时数据、体积数据）
2. **可复用代码**：流式适配层、图片压缩、闹钟 UTS 插件——这三块直接进正式工程
3. **PRD 更新**：把 §15.5 的"限制"表换成实测结论，去掉"待验证"
4. **架构决策**：每条降级对应一条 ADR，写清为什么这么选

---

## 8. 不做什么（防止 PoC 膨胀）

- 不做登录、鉴权、多档案
- 不接真实大模型，不调真实 OCR（桩服务足够）
- 不还原 UI 设计稿
- 不做性能优化（只测现状，不调优）
- 不做 iOS
- 不写单测

> PoC 允许代码丑。它只回答"能不能"，不回答"好不好"。
