# 明路 UI 改版要点

> 配套原型：[ui-redesign-prototype.html](./ui-redesign-prototype.html)（浏览器打开后可切换首页、健康对话、找医生、健康和我的）
>
> 本方案依据当前 16 张安卓页面截图及《明路 PRD V3.1》整理，聚焦视觉方向和信息架构，不提供逐页实现代码。原型中的姓名、指标、医生和提醒均为示意内容。

## 1. 改版目标

当前界面已具备登录、问答、提醒、角色、家庭档案、报告和健康时间线等基础能力，但视觉主要由同色背景、白色表单卡片和深绿按钮构成。页面之间缺少明确的主次，首页更像功能目录，复杂表单连续堆叠，健康记录与对话陪伴也没有形成统一体验。

改版建议围绕三件事展开：

- **更快开始**：把“我现在可以做什么”放在各页面第一屏，减少用户在入口间寻找。
- **更易理解**：用标题、分组、卡片和辅助说明建立稳定层级，尤其提升指标与提醒的可读性。
- **更有信任感**：使用安静、克制的健康视觉；医疗边界、数据归属和操作结果说清楚。

## 2. 视觉方向

建议采用“温润自然、清楚可靠”的轻健康风格，避免传统医疗蓝白，也避免过度可爱或过度拟物。原型加入三套可切换主题：自然绿、海盐蓝、暖阳杏；从“我的 → 外观主题”选择，偏好保存在当前浏览器。

| 维度 | 建议方向 |
|---|---|
| 主色 | 默认使用深松绿；海盐蓝和暖阳杏作为偏好主题。主色用于主要操作和导航选中态，浅色用于健康状态、标签与辅助高亮 |
| 背景 | 暖白为页面主背景，浅灰绿承载次级分区；大面积纯色背景减少为低对比底色 |
| 强调色 | 柔和琥珀色仅用于提醒、待处理和次要强调，不用颜色单独表达严重性 |
| 字体层级 | 页面标题、卡片标题、数值、解释文字形成 4 级；数字和单位分层，不用一整行小字承载关键信息 |
| 卡片 | 统一圆角、内边距和细边框；减少粗重阴影，以间距和浅色区块区分层级 |
| 图标 | 统一线性图标语义和视觉重量，表情符号仅用于轻量人格表达，不作为重要功能图标 |
| 动效 | 仅为页面切换、反馈和轻量状态变化提供短动效；不影响操作反馈和低端设备性能 |

原型当前采用的色彩起点：松绿 `#24695B`、浅薄荷 `#E6F2ED`、暖白 `#FBFCF9`、文字 `#1D3734`。这组颜色是方向稿，进入开发前仍应做文字对比度和色弱状态检查。

## 3. 导航与页面层级

### 安卓 App

- 底部主导航建议调整为“首页 / 找医生 / 问助手 / 健康 / 我的”，中间的“问助手”作为持续可见的主入口，尺寸和底色明显高于普通导航项。
- 中间入口在导航栏正常布局范围内完整容纳，不依赖负 margin 或溢出触摸区域；进入对话后保持选中态。
- 首页承担健康助手入口和今日概况，不再重复堆叠所有功能入口。
- “健康”聚合快速记录、指标趋势、报告和健康时间线；首页只展示少量最近状态与待办。
- 对话、预问诊、报告解读等沉浸流程进入二级页面，保留清晰的返回和就诊人上下文。

### 微信小程序

- 将相同视觉语言用于小程序，但按 PRD 能力矩阵调整入口：小程序健康管理能力受限；健康时间线为只读；提醒说明应明确日历或单次通知能力。
- 角色自定义、会员购买、持续定时提醒等不应在小程序中伪装成可用功能。跨端提示使用“完整功能需在 App 中使用”等合规表达。
- **工程核对项**：仓库说明指出当前 `android/manifest.json` 的蒸汽模式配置无法直接产出小程序，需要确认实际分支/构建配置和 PRD 的同源目标。UI 原型不代表已验证三端编译。

## 4. 重点页面改造

| 页面 | 现有体验问题 | 改造要点 |
|---|---|---|
| 首页 | 入口平铺，问答、提醒、记录和最近活动权重接近 | 采用问候与就诊人切换、主行动卡、常用快捷入口、今日安排、最近记录的顺序；首屏只保留一项强主行动 |
| 健康对话 | 页面主体和输入框视觉较弱，健康信息缺少结构化总结 | 对话气泡区分助手与本人；支持来源/提示卡片；底部输入区固定；保留就诊人标识与不诊断提示 |
| 找医生 | 搜索、科室、医生列表需要更明显的阅读节奏 | 顶部用自然语言描述入口，搜索与科室筛选分层；医生卡片突出科室、擅长、响应预期、价格和咨询动作 |
| 健康首页 | 打卡、报告和时间线的关系不够直观 | 首屏显示所选就诊人、近期数据概览和记录动作；指标卡标明单位、时间、记录次数及趋势；异常提示使用文字加图形 |
| 健康时间线 | 事件卡片内容连续，难快速定位类型和日期 | 使用日期分组与类型标记；支持报告、咨询、用药、指标筛选；重要操作如摘要导出独立呈现 |
| 提醒 | 类型选择、输入字段、重复日期与说明在长表单中连续出现 | 分为提醒类型、内容、时间与重复、通知说明、保存操作；用分步或折叠区降低单屏负担；小程序说明平台限制 |
| 就诊人管理 | 新建表单字段密集，切换与编辑能力不突出 | 用档案卡展示关系和关键资料完整度；“当前使用”明确；创建流程分组并解释数据归属 |
| 我的 | 多个功能列表同级，重要的健康与隐私入口不够突出 | 按健康与家人、助手设置、隐私与支持分组；会员信息克制呈现；记忆查看/删除和隐私授权容易找到 |
| 角色中心 / 记忆 | 列表信息重复、创建操作与角色状态不突出 | 角色卡突出名称、语气和当前状态；记忆按就诊人展示，编辑和删除入口有明确确认反馈 |
| 报告上传 | 上传区域与后续识别预期较弱 | 用清晰上传大区域说明支持格式和用途；上传后显示处理中、成功、失败状态；对识别结果标注来源与人工核对提醒 |

## 5. 关键交互原则

- **就诊人上下文持续可见**：切换档案时明确当前对象；问答、提醒、记录和报告均展示所属就诊人。
- **主操作优先且唯一**：每屏突出一个主要操作，次要操作使用描边或文字按钮，避免多个深绿色按钮竞争。
- **助手入口持续可达**：底部中间的“问助手”从主要页面一键进入对话；首页主视觉按钮也可进入同一对话，形成固定入口与场景入口两条路径。
- **主题不改变语义**：主题只调整颜色和表面层次，不改变指标含义、风险级别或按钮状态；切换后仍维持文字对比度和状态标签可辨识。
- **状态不靠颜色单独传达**：提醒、健康数据、上传和咨询状态均配有文字标签或图标。
- **表单渐进披露**：必填项先出现，补充项折叠或分组；日期、频次和单位提供上下文说明。
- **医疗表达保持克制**：产品整理信息、提示就医路径，不给出诊断、处方和疗效承诺；紧急情形显示清楚的求助指引。
- **空状态指导下一步**：没有记录时告诉用户如何开始，不使用大块留白或仅显示“暂无数据”。
- **操作反馈明确**：创建、保存、上传、删除、切换就诊人均提供成功/失败反馈，危险操作支持撤销或二次确认。

## 6. uni-app x / 蒸汽模式落地提示

原型用于视觉和信息架构沟通，不能直接作为生产页面代码。开发拆解时建议先将视觉规范落实为受支持的基础样式，再逐页实现：

- 蒸汽模式样式遵循项目已有约束：不使用后代/子代选择器；`display` 仅用 `flex` 或 `none`；避免依赖动态 `:class` 更新选中态。
- 点击态、筛选态和就诊人选择使用项目已验证的渲染方式；事件绑定调用函数，不在模板事件中直接赋值。
- 控件按小程序与安卓的可点击区域、键盘、滚动和安全区分别校验，不能只以浏览器原型判断触摸体验。
- 图表在一期优先采用轻量趋势线/柱形呈现；提供数值与文字说明，避免把颜色当作数据本身。
- 先做首页、对话、健康记录和我的四类核心页面，再迁移提醒、档案、时间线、角色和报告等长尾页面。
- 小程序端需验证自定义 tabBar 中心主入口的尺寸、切换行为及安全区；若采用平台原生 tabBar，则需评估中心入口的视觉限制。
- 主题偏好建议保存为有限的设计 token 组合，并校验文字、图标、图表和状态色，不在页面内自由拼接颜色。

## 7. 建议实施顺序

1. **定基线**：确认 Android 与小程序构建目标、导航能力、状态栏/安全区和现有页面入口。
2. **定视觉规范**：色板、字号、间距、圆角、按钮、输入框、状态标签和图标统一。
3. **改核心主链路**：首页 → 健康对话/预问诊 → 找医生；验证家庭档案上下文是否贯穿。
4. **改健康数据**：记录、提醒、报告和时间线共享同一套数据卡片与状态表达。
5. **改设置和长表单**：就诊人、角色、记忆、隐私和报告上传统一分组及空/错误/成功状态。
6. **按端适配**：逐页核对安卓和小程序功能矩阵、可用导航、交互反馈和小屏溢出。

## 8. 原型范围

HTML 原型包含首页、健康对话、找医生、健康档案和我的五个代表性页面，并支持页面切换、居中的助手主入口、三套主题选择和轻量反馈。主题偏好保存在本地浏览器。提醒、时间线详情、档案编辑、角色、记忆和报告页以本文件中的改造要点为后续设计依据，原型暂不展开这些流程，也没有连接真实 API。
